    4. VAE

    This report trains a variational autoencoder (VAE) on MNIST and follows the statement's thread, the tug of war inside the loss. A VAE pays for two things at once: reconstructing its input, and keeping each code distribution \(q(z\mid x)\) close to the prior \(\mathcal N(0, I)\). So every loss below is reported as its two terms, separately, in nats per image: summed over the 784 pixels (or the \(d\) latent dimensions) and averaged over the images. Exercise 1 trains a VAE with a 16-dimensional latent space. Exercise 2 retrains the same model with \(d = 2\), so the latent space can be drawn, and measures what that costs.

    Statement, re-running and seeds

    • Statement: Exercises → 4. VAE (2026.2)
    • Re-run from the repository root with python docs/exercises/vae/code/main.py. MNIST is downloaded to ./data/ (git-ignored). The script writes figures/fig1.png … fig6.png and prints every number quoted in this report, each with a label.
    • Seeds: torch.manual_seed(42) right before building each model (first \(d=16\), then \(d=2\)), the split generator torch.Generator().manual_seed(42) from the statement, and torch.manual_seed(0) right before Figure 3's prior samples. Weight initialisation, mini-batch shuffling and every \(\varepsilon\) of the reparameterization come from these seeds, so a re-run reproduces every number exactly. I ran the script four times on the same machine, and every training and test number came out identical. Another CPU or library version may change the last decimals.
    • Run time: about one minute of training per model on a CPU (8 threads, torch 2.15, Windows 11). In the final run that was 63.9 s for \(d=16\) and 71.2 s for \(d=2\), and 144 s for the whole script including data preparation, figures and diagnostics. Across four runs on a machine shared with other jobs, the per-model time ranged from 59 to 71 s.
    • Code: code/vae.py holds the model, the reparameterization, the two loss terms and the train/evaluate loops. code/main.py is the single entry point: data, both experiments, Figures 1–6 and the diagnostics used in the analyses.

    Design decisions, stated once for the whole report:

    1. Single-sample estimates everywhere. Validation and test numbers use the same pass as training: encode, draw one \(z = \mu + \sigma\odot\varepsilon\) per image, decode. They are one-sample estimates of exactly the loss being optimised.
    2. Test set only at the end. All hyperparameters are fixed by the statement, and nothing is tuned or early-stopped. Validation is the only thing watched during training. The test images are turned into a tensor only after the \(d=16\) training ends. They are then used for the final numbers and for Figures 2, 4 and 6, which the statement defines on test images.
    3. One process, no checkpoints. Both models are trained in the same run of main.py, so Figure 6 uses the \(d=16\) model still in memory. No weights are written to disk or to git.
    4. Decoder outputs are shown as grey levels. Figures 2, 3, 5 and 6 display the decoder's Bernoulli means \(\hat x\in(0,1)^{784}\) directly. No pixels are sampled.

    Exercise 1

    I wrote the VAE in PyTorch and let autograd compute the gradients. The reparameterization, both loss terms and the prior sampling are written by hand in vae.py and main.py. The \(d=16\) model is built right after torch.manual_seed(42) and trained for 20 epochs with Adam (learning rate \(10^{-3}\), batch 128, \(\beta = 1\)). Reconstruction and KL are logged separately on train and validation every epoch, and the test set is evaluated once, after training.

    def load_split():
    """The statement's split, verbatim: 50 000 train / 10 000 validation from
    the official training set (generator seeded with 42); the official 10 000
    test images are the test set."""
    train_full = datasets.MNIST("data", train=True, download=True, transform=transforms.ToTensor())
    test = datasets.MNIST("data", train=False, download=True, transform=transforms.ToTensor())
    train, val = random_split(train_full, [50_000, 10_000],
                              generator=torch.Generator().manual_seed(42))
    return train, val, test


def flatten(dataset):
    """Run every image through the dataset's own ToTensor transform once
    (pixels in [0, 1]) and stack them into an (N, 784) tensor + (N,) labels.
    Doing it once instead of every epoch only saves time; values are identical."""
    xs, ys = zip(*(dataset[i] for i in range(len(dataset))))
    return torch.stack(xs).view(len(xs), 784), torch.tensor(ys)


def make_loaders(train_xy, val_xy):
    """Mini-batches of 128. Only the training loader shuffles; its order is
    drawn from torch's global RNG, which was just seeded with 42."""
    train_loader = DataLoader(TensorDataset(*train_xy), batch_size=BATCH_SIZE,
                              shuffle=True, num_workers=0)
    val_loader = DataLoader(TensorDataset(*val_xy), batch_size=BATCH_SIZE,
                            shuffle=False, num_workers=0)
    return train_loader, val_loader

    B — Build the model

    Part Layers \(d=16\) shapes
    Encoder Linear(784, 512) → ReLU → Linear(512, 256) → ReLU \(784 \to 512 \to 256\)
    Heads mu_head = Linear(256, d), logvar_head = Linear(256, d) \(256 \to 16\) twice
    Decoder Linear(d, 256) → ReLU → Linear(256, 512) → ReLU → Linear(512, 784) → sigmoid \(16 \to 256 \to 512 \to 784\)

    The \(d=16\) model has 1,079,600 parameters, and the \(d=2\) model has 1,068,820. The loss for one image is

    \[ \mathcal L(x) \;=\; \underbrace{-\sum_{j=1}^{784}\Big[x_j\log\hat x_j + (1-x_j)\log(1-\hat x_j)\Big]}_{\text{reconstruction (BCE)}} \;+\; \beta\cdot\underbrace{\frac12\sum_{i=1}^{d}\Big(\mu_i^2+\sigma_i^2-1-\log\sigma_i^2\Big)}_{\mathrm{KL}\left(q(z\mid x)\,\|\,\mathcal N(0,I)\right)}, \qquad \beta = 1, \]

    averaged over the images of the batch. Each piece is written by hand:

    • Reparameterization. The encoder outputs \(\mu\) and \(\log\sigma^2\). Predicting the log-variance lets the head output any real number while \(\sigma^2 = e^{\log\sigma^2}\) stays positive. The sample is \(z = \mu + \sigma\odot\varepsilon\) with \(\sigma = \exp(\tfrac12\log\sigma^2)\) and \(\varepsilon\sim\mathcal N(0, I)\). The noise does not depend on any parameter, so \(\partial z/\partial\mu = 1\) and \(\partial z/\partial\sigma = \varepsilon\), and the reconstruction gradient reaches the encoder.
    • Reconstruction. This is the Bernoulli negative log-likelihood above: F.binary_cross_entropy(x_hat, x, reduction="sum") adds it over all \(B\times784\) pixels, and dividing by the batch size \(B\) leaves nats per image. reduction="mean" would also divide by 784, which is the same as secretly setting \(\beta\approx 784\).
    • KL. The closed form for two diagonal Gaussians is written out term by term. No torch.distributions is used.
    • loss_terms returns the two terms separately, and the training loop adds them only to take the gradient.

    A sanity check of the scale: the untrained model gives a validation reconstruction of 544.72 nats and a KL of 0.03 nats. A freshly initialised decoder outputs \(\hat x_j \approx 0.5\), which costs \(784\ln 2 = 543.4\) nats, and fresh heads give \(\mu\approx 0\) and \(\log\sigma^2\approx 0\), so the KL is close to 0. A pixel-mean BCE would have printed about 0.69 instead of about 544.

    class VAE(nn.Module):
    """MLP VAE: 784 -> 512 -> 256 -> (mu, log sigma^2) in R^d -> 256 -> 512 -> 784."""

    def __init__(self, d: int):
        super().__init__()
        self.d = d
        # Encoder trunk: 784 -> 512 -> 256, ReLU after each layer.
        self.encoder = nn.Sequential(
            nn.Linear(784, 512), nn.ReLU(),
            nn.Linear(512, 256), nn.ReLU(),
        )
        # Two separate linear heads 256 -> d read the same features: one gives
        # the mean mu of q(z|x), the other its log-variance log sigma^2.
        # Predicting log sigma^2 (any real number) keeps sigma^2 = exp(.) > 0.
        self.mu_head = nn.Linear(256, d)
        self.logvar_head = nn.Linear(256, d)
        # Decoder: d -> 256 -> 512 -> 784, ReLU on the hidden layers and a
        # sigmoid at the output, so each of the 784 outputs is a Bernoulli
        # mean: the probability that the pixel is "on".
        self.decoder = nn.Sequential(
            nn.Linear(d, 256), nn.ReLU(),
            nn.Linear(256, 512), nn.ReLU(),
            nn.Linear(512, 784), nn.Sigmoid(),
        )

    def encode(self, x):
        """x: (B, 784) in [0, 1]  ->  mu, logvar: (B, d) each."""
        h = self.encoder(x)
        return self.mu_head(h), self.logvar_head(h)

    def decode(self, z):
        """z: (B, d)  ->  x_hat: (B, 784), per-pixel Bernoulli means in (0, 1)."""
        return self.decoder(z)

    def forward(self, x):
        """One stochastic pass: encode, draw z by reparameterization, decode."""
        mu, logvar = self.encode(x)
        z = reparameterize(mu, logvar)
        return self.decode(z), mu, logvar

    def reparameterize(mu, logvar):
    """Draw z ~ N(mu, diag(sigma^2)) as a differentiable function of (mu, logvar).

    z = mu + sigma * eps with eps ~ N(0, I). The randomness lives in eps, which
    does not depend on any parameter, so dz/dmu = 1 and dz/dsigma = eps: the
    reconstruction gradient can flow back through z into the encoder.
    """
    sigma = torch.exp(0.5 * logvar)   # sigma = exp(log(sigma^2) / 2)
    eps = torch.randn_like(sigma)     # standard normal noise, shape (B, d)
    return mu + sigma * eps

    def loss_terms(x, x_hat, mu, logvar):
    """Return (recon, kl), each in nats per image.

    recon = -sum_j [x_j log x_hat_j + (1 - x_j) log(1 - x_hat_j)]   over the 784 pixels
    kl    = 1/2 sum_i (mu_i^2 + sigma_i^2 - 1 - log sigma_i^2)      over the d latent dims
    Both are summed per image and then averaged over the B images of the batch.
    """
    batch_size = x.shape[0]
    # Bernoulli negative log-likelihood. reduction="sum" adds the BCE over all
    # B x 784 pixels; dividing by B leaves nats per image. reduction="mean"
    # would also divide by 784, i.e. secretly set beta ~ 784.
    recon = F.binary_cross_entropy(x_hat, x, reduction="sum") / batch_size
    # Closed-form KL( N(mu, diag sigma^2) || N(0, I) ), written out term by
    # term (sigma^2 = exp(logvar)), summed over dims and batch, divided by B.
    kl = 0.5 * torch.sum(mu.pow(2) + logvar.exp() - 1.0 - logvar) / batch_size
    return recon, kl

    C — Train

    train runs Adam (learning rate \(10^{-3}\)) on recon + \(\beta\cdot\)KL for 20 epochs of batch-128 mini-batches. After each epoch it records four numbers: the reconstruction and KL training terms, averaged over that epoch's mini-batches while the weights move, and the same two terms on the validation set for the end-of-epoch model. fit_vae does the seeding, the building and the loaders in that order, and is called unchanged for \(d=16\) and \(d=2\). test_numbers runs once per model, after its training.

    def run_epoch(model, loader, beta=1.0, optimizer=None):
    """One pass over `loader`; returns the mean (recon, kl) in nats per image.

    With an optimizer it trains; without one it only evaluates (no gradients).
    Evaluation uses the same single-sample reparameterized pass as training,
    so validation and test numbers are one-sample estimates of the same loss.
    """
    training = optimizer is not None
    model.train(training)
    total_recon, total_kl, n_images = 0.0, 0.0, 0
    with torch.set_grad_enabled(training):
        for x, _ in loader:                    # labels are never used by the VAE
            x_hat, mu, logvar = model(x)       # encode -> sample z -> decode
            recon, kl = loss_terms(x, x_hat, mu, logvar)
            if training:
                loss = recon + beta * kl       # negative ELBO per image (beta = 1)
                optimizer.zero_grad()
                loss.backward()                # autograd: decoder -> z -> encoder
                optimizer.step()
            b = x.shape[0]                     # the last batch is smaller, so
            total_recon += recon.item() * b    # weight each batch mean by its size
            total_kl += kl.item() * b
            n_images += b
    return total_recon / n_images, total_kl / n_images


def evaluate(model, loader, beta=1.0):
    """(recon, kl) of a fixed model on `loader`, in nats per image."""
    return run_epoch(model, loader, beta)


def train(model, train_loader, val_loader, epochs=20, lr=1e-3, beta=1.0):
    """Adam on the negative ELBO; logs both terms on train and validation every epoch."""
    optimizer = torch.optim.Adam(model.parameters(), lr=lr)
    history = {"train_recon": [], "train_kl": [], "val_recon": [], "val_kl": []}
    for epoch in range(1, epochs + 1):
        # Training terms: averaged over the epoch's mini-batches while the weights move.
        tr_recon, tr_kl = run_epoch(model, train_loader, beta, optimizer)
        # Validation terms: the model as it stands at the end of the epoch.
        va_recon, va_kl = evaluate(model, val_loader, beta)
        for key, value in zip(history, (tr_recon, tr_kl, va_recon, va_kl)):
            history[key].append(value)
        print(f"  epoch {epoch:2d} | train recon {tr_recon:7.2f}  KL {tr_kl:6.2f}"
              f" | val recon {va_recon:7.2f}  KL {va_kl:6.2f}")
    return history

    def fit_vae(d, train_xy, val_xy):
    """Seed -> build -> loaders -> train, identical for d=16 and d=2."""
    torch.manual_seed(42)                       # the statement's seed, before building
    model = VAE(d)
    print(f"[1B/2A] VAE(d={d}): {sum(p.numel() for p in model.parameters()):,} parameters")
    train_loader, val_loader = make_loaders(train_xy, val_xy)
    init_recon, init_kl = evaluate(model, val_loader)   # "epoch 0": untrained model
    print(f"  epoch  0 | (untrained)                      | val recon {init_recon:7.2f}"
          f"  KL {init_kl:6.2f}")
    t0 = time.perf_counter()
    history = train(model, train_loader, val_loader, epochs=EPOCHS, lr=LR, beta=BETA)
    history["seconds"] = time.perf_counter() - t0
    history["init_val_recon"], history["init_val_kl"] = init_recon, init_kl
    return model, history


def test_numbers(model, test_xy, label):
    """Final numbers only: called once per model, after its training is over."""
    test_loader = DataLoader(TensorDataset(*test_xy), batch_size=BATCH_SIZE, shuffle=False)
    recon, kl = evaluate(model, test_loader)
    print(f"[{label}] test recon      = {recon:.2f} nats/image")
    print(f"[{label}] test KL         = {kl:.2f} nats/image")
    print(f"[{label}] test neg. ELBO  = {recon + kl:.2f} nats/image")
    return recon, kl

    def tile(images, nrows, ncols, pad=2):
    """Lay (nrows*ncols, 784) images out row-major in one array, with white
    `pad`-pixel separators. Returns the canvas and the tile-centre coordinates."""
    imgs = np.asarray(images).reshape(nrows, ncols, 28, 28)
    step = 28 + pad
    canvas = np.ones((nrows * step + pad, ncols * step + pad))
    for r in range(nrows):
        for c in range(ncols):
            canvas[pad + r * step: pad + r * step + 28, pad + c * step: pad + c * step + 28] = imgs[r, c]
    centres_x = pad + np.arange(ncols) * step + 13.5
    centres_y = pad + np.arange(nrows) * step + 13.5
    return canvas, centres_x, centres_y

    E — Analysis

    1. Why the KL rises while the total falls. The untrained model starts at a validation KL of 0.03 nats. Every \(q(z\mid x)\) is then almost the prior, so \(z\) says nothing about \(x\), and the untrained decoder outputs a flat grey image (every pixel near 0.5), which costs 544.72 nats of reconstruction. The KL term is the price of making \(q(z\mid x)\) differ from the prior, that is, of letting the code carry information about this particular image. Averaged over the data it is an upper bound on the mutual information \(I(x; z)\) that the code transmits. The decoder can only reconstruct better if \(z\) tells it more, and that information has to be paid for in KL. With \(\beta = 1\), buying one more nat of KL lowers the total as long as it removes more than one nat of reconstruction. Figure 1 gives a rough exchange rate:

    Validation, epochs \(\Delta\) recon (nats) \(\Delta\) KL (nats) \(\lvert\Delta\) recon\(\rvert\) / \(\Delta\) KL
    0 → 1 −417.68 (544.72 → 127.04) +13.55 (0.03 → 13.58) 30.8
    1 → 5 −34.02 (127.04 → 93.02) +4.19 (13.58 → 17.77) 8.1
    5 → 20 −11.44 (93.02 → 81.58) +2.46 (17.77 → 20.23) 4.7

    These ratios are only a rough exchange rate. Part of each drop in reconstruction comes from the decoder getting better at a fixed amount of information, not from the extra KL. Still, they show the trade: early on, each nat of KL goes together with many nats of reconstruction, so the optimizer chooses to pay more KL. The validation KL rises from 13.58 nats at the first epoch to 20.23 nats at the last, while the validation total falls from 140.62 to 101.81 nats. The ratio shrinks as training goes on, because the most useful information gets encoded first. The KL is still creeping up at epoch 20 (+0.47 nats in the last epoch), so the trade has not reached its balance yet. The KL is also spent only where it pays: 4 of the 16 latent dimensions stay unused, with \(\mathrm{Var}[\mu_i] < 0.01\) and \(\mathbb E[\sigma_i^2]\) between 0.949 and 0.998, so \(q(z_i\mid x) \approx \mathcal N(0,1)\) and they cost almost no KL.

    2. Two reasons Figure 3 looks worse than Figure 2.

    (a) Where the prior samples land. Figure 2 decodes \(\mu(x)\) of a real image. That is a point in the region the decoder was trained on. Figure 3 decodes \(z\sim\mathcal N(0, I)\). That only works if the aggregate posterior \(q(z) = \frac1N\sum_n q(z\mid x_n)\), the cloud of codes the decoder actually saw, fills the prior. It does so only on average. Its per-dimension variance, \(\mathrm{Var}[\mu_i] + \mathbb E[\sigma_i^2]\), lies between 0.95 and 1.08, so the second moments match the prior. Its shape does not. In the 12 active dimensions each posterior is narrow (mean \(\sigma = 0.229\)) compared with the spread of the means (0.967). So \(q(z)\) is a union of small blobs, one cluster of blobs per kind of digit, with gaps between the clusters that the prior still fills. The bad tiles of Figure 3 are the draws that landed in those gaps. I cannot read 11 of the 64 tiles as any digit: (row, column) (1,4), (2,6), (4,7), (5,3), (6,3), (7,2), (7,3), (8,3), (8,4), (8,6) and (8,7). 10 of those 11 are draws whose 10 nearest real codes (the codes of 5 000 validation images) have no digit holding more than half of them. Only (6,3) is the exception. The same test over many draws shows this is systematic. 38.6 % of prior draws have no majority digit among their neighbours, against 8.6 % of codes sampled from \(q(z\mid x)\) for the other 5 000 validation images, 4.5 times as often. The median share of the most common digit is 60 % for prior draws against 90 % for real codes. Between digit regions, the decoder never had to draw one single digit. A second check, on density, flags other draws: prior draws have a median \(\log q(z)\) 18.5 nats below real codes. But the 10 Figure 3 tiles it flags as lowest-density are still legible digits, if often unusually bold.

    (b) What the decoder outputs for a given \(z\). Even at a well-placed \(z\), the decoder does not output a digit. It outputs \(\hat x = \mathbb E[x\mid z]\), the probability that each pixel is on under a per-pixel Bernoulli model, and the figures show those probabilities. When several sharp images are consistent with the same code (a stroke slightly left or right, thicker or thinner), the output that minimises BCE is their average, and an average of shifted strokes is a grey blur. This is the lecture's conditional-mean argument, with a Bernoulli likelihood in place of the Gaussian one. There is no bug here: the objective gets what it asks for. The numbers show it. Real validation images have 8.6 % of their pixels strictly between 0.1 and 0.9. The decoded \(\mu\) reconstructions have 14.8 % and the prior samples 16.7 %. The total entropy of the decoder's 784 Bernoulli outputs is 80.9 nats per image for reconstructions from \(\mu\), close to the 80.78-nat test reconstruction term. That is the amount of pixel detail the decoder admits it cannot pin down from \(z\). For prior samples it is 90.2 nats. Reason (b) holds for every \(z\), and it is why even the Figure 2 reconstructions are softer than the originals. The two reasons add up: a prior draw that lands between digit regions (a) is consistent with images of several digits, so the average in (b) blends whole shapes and not just stroke positions. That produces the "no digit at all" tiles.

    3. Why decode \(\mu\) in Figure 2. \(\mu(x)\) is the centre, both mean and mode, of \(q(z\mid x)\), so it is the encoder's single best guess of the code. A sampled \(z = \mu + \sigma\odot\varepsilon\) adds noise with a mean \(\sigma\) of 0.229 per active dimension. The figure would then show one random reconstruction, which changes with the seed, instead of what the encoder learned. It is also measurably worse. On the validation set, decoding \(\mu\) gives a reconstruction term of 76.21 nats, against 81.54 nats with one sampled \(z\), 5.33 nats more. Sampling is needed during training, because the ELBO is an expectation over \(q(z\mid x)\) and the noise forces nearby codes to decode to similar images. To display a reconstruction, the deterministic, most probable code is the right choice.

    C — The decoded plane

    Figure 5 decodes a \(15\times15\) grid with \(z_1, z_2 \in \Phi^{-1}(q)\), where \(q = 0.05, 0.114, \dots, 0.95\) (15 evenly spaced values, scipy.stats.norm.ppf), so the grid runs from −1.645 to 1.645 on each axis. The tiles keep the orientation of Figure 4: \(z_1\) grows to the right and \(z_2\) grows upwards.

    Why this spacing: the \(q\) values are evenly spaced, so consecutive grid lines are separated by the same prior probability \(0.9/14\approx0.064\) along each axis, and since \(\mathcal N(0, I)\) is a product of independent axes, every cell holds the same prior mass, \((0.9/14)^2 \approx 0.41\,\%\). This makes the grid dense near the origin, where the prior and the codes are concentrated, and sparse in the tails.

    E — Analysis

    1. Which digits overlap, in Figure 4 and in Figure 5. To measure the overlap in Figure 4, I looked up the 10 nearest test codes of every test code and counted how many come from another digit. The most mixed pairs are:

    Pair Share of 10 nearest codes from the other digit
    4 – 9 31.5 % (4 → 9: 31.7 %, 9 → 4: 31.3 %)
    3 – 5 22.1 %
    7 – 9 14.3 %
    5 – 8 13.9 %
    3 – 8 11.2 %

    A 9 keeps only 47.4 % of its neighbours among other 9s, a 5 keeps 51.9 % and a 4 keeps 53.9 %, against 96.3 % for a 1 and 92.8 % for a 0. In Figure 4 the 4, 7 and 9 clouds share the region around \(\mu \approx (0 \dots 1.5,\; 0 \dots 1.5)\), while 3, 5 and 8 share the region around \(\mu\approx(-1.5\dots0,\; -2\dots-0.5)\). The 5s also form a second, separate cluster at the top, around \(\mu\approx(-0.4,\; 1.5)\), which Figure 5 decodes as 5s in rows 1–3, columns 4–7. The 0s (left) and the 1s (bottom right) sit apart.

    The same 4 → 9 transition runs through the top-right of Figure 5. Columns 9–10 (\(z_1 = 0.16\)–\(0.33\)) in rows 2–4 (\(z_2 = 0.70\)–\(1.20\)) are open-top 4s. Columns 9–10 in rows 7–9 (\(z_2 = -0.16\)–\(0.16\)) are round 9s. In between, the 4s turn into 9s in two directions. Going right along row 3 (\(z_2 = 0.92\)), columns 9–10 are 4s, column 11 is the hybrid, and column 12 is a round 9. Going down column 10 (\(z_1 = 0.33\)), rows 2–4 are 4s, row 5 is the hybrid, and rows 6–9 are 9s. The 10 nearest validation codes of those grid points confirm that this is the 4/9 boundary. Along row 3, at columns 10, 11 and 12, they are 100 % 4s, 70 % 4s and 70 % 9s. Down column 10, the share of 4s falls from 100 % (rows 2–3) to 60 % (row 5) and 50 % (row 6). In the overlap the decoder has to draw a single image. At row 3, column 11, where 7 of the 10 nearest codes are 4s, it already draws a 9-like hybrid rather than a 4. The in-between images are not two digits superimposed. Each is a single connected stroke: a 4 whose two upper strokes have bent towards each other and closed into a narrow, pointed loop. It reads as a 4 or as a 9, and it is blurrier than the prototypes on either side. The 3–5 overlap appears the same way in the bottom-left corner. Along row 13 (\(z_2 = -0.92\)), columns 1–3 are 5s, columns 4–5 are 3s and columns 6–7 are 5s again, so here the 3s sit between two bands of 5s. In the transition tiles of row 12 (columns 4–5), a 3 carries a faint vertical stroke at its upper left, the start of a 5's top bar.

    2. What two numbers per image force the model to throw away. The KL bounds how much information the code carries. At 6.68 nats ≈ 9.6 bits per image for \(d=2\), against 20.25 nats ≈ 29.2 bits for \(d=16\), the 2-D code can hold about a third as much. Naming the digit alone takes \(\log_2 10 \approx 3.3\) bits, which leaves only about 6 bits for everything else. What goes is most of the style: the exact shape of loops and tails, most of the variation in stroke thickness, and the quirks of each writer. Figure 5 is the evidence. Its 225 tiles contain only about ten prototypes, roughly one region per digit (the 5s get more than one), and inside a region the image changes along just one or two smooth directions. The 1s in columns 13–15, rows 11–15 change only their slant. The 0s in column 1 change only their slant and roundness. The 8s in columns 8–10, rows 10–15 change only their lean. No tile shows a broken stroke, a stray mark or an unusual loop, although the test set has many: test

    8, the 5 in Figure 2, has a detached top bar.

    Whatever the code cannot specify, the decoder averages. The Figure 5 tiles have 26.6 % grey pixels and a Bernoulli entropy of 139.3 nats per tile, against 14.8 % and 80.9 nats for \(d=16\) reconstructions. That averaging is where the extra 55.15 nats of reconstruction go. Part of the identity is lost as well: a 10-nearest-neighbour classifier on the codes recovers the digit for 77.9 % of test images with \(d=2\), against 95.5 % with \(d=16\). The overlapping regions in question 1 are where those identities get lost.

    3. The two rows of Figure 6. Only the bottom (latent) row passes through images that look like digits. The top row is a cross-fade. For \(t\) between 0.33 and 0.67 each frame shows a 2 and a 0 at partial intensity: the 2's diagonal and base show through the 0's loop. Only 24.9 % of the inked pixels of the two images coincide, so most strokes become half-intensity ghosts. The \(d=16\) VAE itself rates these frames as unlike MNIST. Their negative ELBO (decoding \(\mu\)) rises from 101.7 nats at \(t=0\) and 98.5 nats at \(t=1\) to 268.0 nats at \(t=0.33\), against an average of 96.44 nats for validation images. The bottom row turns the 2 into the 0 through shapes that are each a single, continuous stroke: a 2 whose base curls into a loop, a 3- or 8-like shape at \(t = 0.33\)–\(0.44\), a 5- or 6-like shape at \(t = 0.56\), then an open 0. Scored the same way, its frames never go above 147.6 nats (at \(t = 0.44\)). Even the endpoints score 119.2 and 105.1, because they are grey reconstructions. The two rows are equally grey in the middle: at \(t = 0.44\), 26.4 % of the pixel-space frame's pixels are grey against 25.1 % for the latent frame, and they score 265.7 against 147.6 nats. So the difference is not blur. It is structure: two overlapping digits against one plausible stroke.

    The reason is where each straight line runs. Images of digits do not form a convex set in pixel space: the average of two digit images is almost never a digit image, so the straight pixel-space line leaves the data manifold as soon as \(t > 0\). The decoder, on the other hand, was trained to map every code near the data to a digit-like image. The KL pulls codes together and the sampling noise forces whole neighbourhoods of \(z\) to decode sensibly. A straight line between two codes therefore stays inside the region the decoder knows, and once decoded it becomes a curved path in pixel space that stays close to the manifold of handwritten digits.
